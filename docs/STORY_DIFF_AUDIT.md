## 3. Детали по FAIL и WARN

### FAIL-1. Нарушение чётности ID в `mymod_relay_02_turnin`

В диалоге сдачи Q2 (строки 2046–2069):

```xml
<phrase id="1">
    <text>mymod_relay_02_turnin_phrase_1_text</text>
    <next>2</next>
    <next>3</next>
</phrase>
<phrase id="2">
    <text>mymod_relay_02_turnin_phrase_2_text</text>
    <precondition>dialogs.mymod_relay_02_turnin_phrase_2_precondition</precondition>
    <action>dialogs.mymod_relay_02_turnin_phrase_2_action</action>
</phrase>
<phrase id="3">
    <text>mymod_relay_02_turnin_phrase_3_text</text>
</phrase>
```

Текст `mymod_relay_02_turnin_phrase_3_text` — «Ещё ищу. Охрана у Земснаряда.» / «Still looking. The guards are at the dredge.» — это реплика **Игрока**, но `id=3` нечётный, то есть по контракту принадлежит NPC. В результате ветка отказа/«ещё ищу» отображается не на той стороне, а выбор из фразы 1 ведёт на NPC-реплику.

**Соответствие контракту:** нарушен §2.5 и §3.3(13) `API_v2.md` («чётные ID — Игрок, нечётные — NPC»).

**Рекомендуемое исправление:** перенумеровать фразу в чётный `id=4`, заменить `<next>3</next>` на `<next>4</next>`, переименовать ключ в `mymod_relay_02_turnin_phrase_4_text` в `st_last_relay.xml` для `rus` и `eng` (или добавить NPC-ответ `id=5`). После правки ветвление «согласие/отказ» будет соответствовать контракту.

### WARN-1. Жизненный цикл предмета Q2: общий ПДА и отсутствие очистки при отмене

Этап 0 Q2 завершается по `HasItem(itm_pda_common, count=1)` (строки 2564–2569). Предмет создаётся в инвентаре командира отряда через `spawn_npc_item` (2550–2562, Lua 3193–3222). При отмене квеста `_cleanup` (3734–3749) снимает поршни и удаляет отряд, но **не удаляет ПДА** из инвентаря игрока или мира. `_reward` (3708–3731) также не удаляет предмет: это делает только merged-action сдачи (3992–4004).

Последствия:

1. Если игрок подобрал ПДА и отменил Q2, при повторном взятии `HasItem` уже истинно — этап 0 закроется сразу, без похода на Земснаряд.
2. `itm_pda_common` — распространённый предмет; любой такой ПДА в инвентаре игрока до взятия Q2 также сразу удовлетворит условие этапа 0 и позволит сдать квест.

**Рекомендация:** использовать уникальную секцию квестового предмета (например, `itm_pda_quest_decryptor`) либо отдельный инфопоршень-маркер; при отмене удалять предмет через `RemoveItem`/`TakeItem` в `on_fail_actions` или отдельный cleanup-хук. Если общий `itm_pda_common` оставлен намеренно (как в примере §4 `API_v2.md`), риск нужно зафиксировать как известный.

### WARN-2. `_can_turn_in` Q2 не проверяет стадию

`mymod_relay_02_turnin_can_turn_in` (3954–3966) проверяет только наличие задачи:

```lua
if not tsk then return false end
if quest.return_stage >= 0 and (tsk.stage or 0) < quest.return_stage then
    return false
end
return true
```

При `return_stage = -1` (2540) проверка стадии не выполняется, поэтому диалог сдачи открывается сразу после выдачи `mymod_relay_02_taken`. Фактическая сдача защищена только `phrase`-условием `HasItem` (2062, Lua 3981–3989): без ПДА реплика 2 недоступна.

Формально §3.3(10) `API_v2.md` разрешает не проверять `last_stage`, если у диалога есть собственный `HasInfo`; здесь это `mymod_relay_02_taken` (2048). Однако `taken` — не признак готовности, а признак выдачи. Риск: раннее открытие диалога и показ ветки «ещё ищу» (которая к тому же сломана FAIL-1).

**Рекомендация:** добавить в `_can_turn_in` проверку `tsk.stage >= quest.last_stage` при `return_stage < 0` либо ввести поршень готовности `mymod_relay_02_ready` из `Stage.on_start_actions`/`_status` с обязательной очисткой в `cleanup_infos`. Для Q1 аналогичная проверка не требуется: диалог уже гейтится `<has_info>mymod_relay_merc_dead</has_info>` (1995).

### WARN-3. `spawn_npc_item` без повтора; `started` ставится до выполнения start-actions

В `_status` Q2 (3609–3614):

```lua
local start_key = stage_key(quest, stage, "started")
if vget(start_key, 0) == 0 then
    vset(start_key, 1)
    run_actions(stage_data.start_actions, db.actor, nil, "mymod_relay_02_decryptor", stage)
end
```

Ключ `started` выставляется **до** `run_actions`. В `spawn_npc_item` (3193–3222) резолв командира и `alife_create_item` выполняются под `pcall`, результат не проверяется и повторной попытки нет. Если после `SIMBOARD:create_squad` командир ещё не разрешён (`commander_id()` вернул `0`/объект не найден), ПДА может не создаться; поскольку `started=1`, действие больше не выполнится, и этап 0 Q2 станет непроходимым (если у игрока нет своего `itm_pda_common`).

**Рекомендация:** ставить `started=1` только после успешного выполнения критичных действий; для `spawn_npc_item` добавить проверку результата `alife_create_item` и/или отдельный retry-ключ. Дополнительно можно создавать предмет не в том же тике, а на следующем тике `_status` после появления командира.

### INFO. Мёртвый Warfare-хелпер

В скрипте остаётся `spawn_task_squad` (2895–2924) с `sim_squad_warfare.set_target` (2914–2915), `stay_time` (2913, 2917–2918) и `force_online` (2920). В данном проекте он **недостижим**: у всех этапов `capture = nil` (2460, 2487, 2549, 2589), а действий `spawn_squad`/`set_target` в `QUESTS` нет. Story-путь `spawn_story_squad` (3238–3265) этих вызовов не содержит, поэтому требование к Story-спавну выполнено. Хелпер можно удалить как мёртвый код, чтобы статический аудит не находил Warfare-вызовы в Story-моде.

## 4. Итог

- **Блокер:** FAIL-1 — нечётный `id=3` у реплики Игрока в `mymod_relay_02_turnin`. Без исправления мод не соответствует контракту XML-графа.
- **Не блокируют сборку, но требуют решения:** WARN-1 (жизненный цикл ПДА Q2), WARN-2 (раннее открытие сдачи Q2), WARN-3 (устойчивость `spawn_npc_item`).
- **Готово к использованию:** патчи `system.ltx`, привязка 4 диалогов, отсутствие новых профилей, один `<action>` на реплику, порядок тегов, полная локализация `rus/eng`, секции отрядов и задач, идемпотентный Story-спавн, очистка поршней/отрядов при отмене, `target_variants`/`descr_variants`.

**После устранения FAIL-1** мод можно повторно проверить на `READY FOR MERGE`; WARN-1…WARN-3 рекомендуется закрыть или явно принять как известные ограничения.
